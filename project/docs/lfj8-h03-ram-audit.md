# Вариант размещения рабочего состояния H03

Проверен исходный H03 `LFJ8-T-D.bin`, 524 288 байт, SHA-256 `844a11b809cda1f2ccaf90cb6a75666009487ccedd2e8190b7eb46137b855544`. Внутренний ID `LFJ8-18-9E1C`. Предпочтительный диапазон для дальнейшей проверки `[0x806B40, 0x807000)`, 1216 байт с выравниванием 64 байта. Владение им на физическом 9E1C остаётся открытым. Карта M32176F4 задаёт RAM `[0x804000, 0x80A000)`, 24 КиБ. [Идентификация H03](lfj8-9e1c-base.md) · [Renesas 32176, карта памяти][renesas]

## Актуальный состав проектного состояния, 20.11.2026

Прежняя оценка 1080/1116 байт не включает добавленные CAN13, сеанс диагностики, очередь RX и полный набор сохраняемых результатов. Создан [типизированный состав](../targets/lfj8/lfj8_h03_storage.h), размеры и смещения которого извлекаются из объектного файла **M32R**, а не из ABI компьютера. Состояния внутри cycle, can13 и engine_rx учитываются один раз. Буферы остаются раздельными; используется только ранее проверенное объединение Toyota gear/GP.

| Блок | Размер ABI M32R | Кандидат размещения, конец не включён |
| --- | ---: | --- |
| Управление, Toyota GP, фазы, датчики и фильтр кнопок | 1072 байта | [0x806B40, 0x806F70) |
| CAN, диагностика, RX-очередь, сохранённые MAIN/FAST | 492 байта | [0x808E40, 0x80902C) |
| Рабочие представления Toyota и раздельные снимки вызовов | 832 байта | [0x80902C, 0x80936C) |

После объединения MODE-02 и TOY-02 добавлены 24 байта фильтра кнопок, 24 байта квалифицированной нагрузки и 8 байт снимка кнопок. Снимки входа и команды SLU добавили ещё 16 байт. Суммарно **2396 байт** против 1780 байт прежних двух окон: дефицит **616 байт**, ещё без будущих состояний владельца CAN, постоянного журнала, остальных стадий Toyota и контекста платформы. Основное окно сохраняет 144 свободных байта. Второе нужно расширить на 760 байт, поскольку эти 144 байта не используются для переноса объектов через разрыв адресов.

Компоновщик разместил три отдельных объекта без пересечений, с выравниванием по 4 байта. Все 36 записей таблицы размеров и смещений получены из целевого объекта. Между концом второго кандидата и **условной** нижней границей стека 0x809700 остаются 916 байт; это расстояние не является доказанным запасом стека.

Скан нового полуинтервала [0x808E40, 0x80936C) не нашёл фиксированных ссылок из перечисленных ниже классов. Шесть исходных OEM-фрагментов повторно сравнены по всем 24576 байтам RAM; оба кандидата сохранились. Мониторные косвенные записи и переотображение этим не исключены. Новая карта **не присваивает адреса работающей прошивке** и не разрешает стирать/занимать эту память.

Проверка отклоняет неверный ABI и порядок байтов, повреждённые записи, пересечения полей и превышение границ. [Проверка карты](../targets/lfj8/check_h03_storage.py) · [Отчёт](../verification/e4m3-can-9e1c/h03-storage.json) · [Отрицательные сценарии](../tests/test_h03_storage.py)

Для интегратора: использовать единые типы как список текущих объектов, добавлять новые постоянные состояния в этот состав, повторять проверку после изменений заголовков. Закрытие H03-04 требует начальной инициализации, сервисной изоляции и доказательства стека; результат этого раздела закрывает расчёт текущего объёма и проверку предложенного расширения на выбранных OEM-путях.

## Что занимает RAM

| Путь исходного ROM | Фактические записи |
| --- | --- |
| `0x003D94 → 0x0009E0`, до вызова по `0x000AE0` | Задаёт SPI `0x809EFC`, FP `0x808000`. Сбрасывает `[0x808104, 0x808E06)`, пишет `FF` в `0x808100` и при входе через preamble инициализирует указатель сохранения PSW в `0x809F9C` |
| `0x008118 → 0x0404C4 → 0x009184` | Обнуляет полуинтервал `[0x804810,0x8066B4)`, 7844 байта, до основного цикла. Здесь же устанавливаются счётчики фаз и байт события |
| `0x008124 → 0x0089EC → 0x008A04` | Обнуляет первые 13 байт каждой из 16 записей с шагом 14 байт, начиная с `0x8066C4`. Последний затронутый байт `0x8067A2` |
| `0x0405C8 → 0x009184` | В условной ветви обнуляет `[0x804004,0x80480E)`. Нижняя RAM также содержит рабочие таблицы штатного приложения |
| `0x0405D0 → 0x00D4F8 → 0x00F0EC` | В той же условной ветви копирует 4096 байт из ROM `0x030022` в `[0x807000,0x808000)`. Длина из ROM `0x030020` равна `0x1000`. Сервисные пути адресуют этот массив через индексы, например в `0x00D784` и `0x00DB84` |
| `0x00C354–0x00C370 → 0x00A82C` | Перед CAN-передачей записывает 32-битную метку по `0x806B24`. Последний доказанный занятый байт непосредственно перед зазором — `0x806B27` |

Скан всех 524 288 байт исходного ROM в диапазоне кандидата не дал выровненных `LD24`, абсолютных 32-битных литералов или непосредственных адресов от штатного FP. Невыровненное совпадение `0x0000FD → 0x806C00` образовано границей двух слов векторной таблицы `0000806C 00008070`. Скрипт отдельно отмечает это совпадение. Декодирование указателей не охватывает вычисляемую адресацию, DMA, переотображение памяти и доступ из обслуживающих программ.

## Сервисная запись и границы доказательства

В ROM есть рассчитанный сервисный адресатор `0x00DBBC–0x00DC10`, чья область включает все байты кандидата. Два прямых пути к функции `0x00D574` идут из `0x00D154` и `0x00D1F0`. Общий диспетчер `0x00D108` каждый раз записывает `0x8066AC` по двум байтам конфигурации в ROM `0x03001B/0x03001C`. Оба байта точного H03 равны нулю, поэтому ветви по маскам 1 и 2 в `0x00D14E` и `0x00D1EA` пропускают вызовы независимо от прежнего значения RAM. Диспетчер достижим из обычной фоновой задачи через `0x040348`. Флаг специального режима `0x804887 == 4` не является условием этой блокировки.

Существующая конфигурация закрывает эту конкретную ветвь записи до перехода к обработчику. Отдельные диагностические чтения используют рассчитанные адреса до `0x8096FF`, например `0x045342`, а проверка диапазона регистрации диагностических указателей находится в `0x04605C–0x046072`. В карте 32176 диапазон кандидата принадлежит блоку `FESBANK0`. H03 в `0x003550–0x0035B4` меняет `FEMMOD` и `FESBANK1` для соседнего блока `0x807000`. Само отсутствие прямого обращения к `FESBANK0` не ограничивает косвенный доступ к нему. [Renesas 32176, §§ 6.4.5 и 6.6][virtual-flash]

Для целевого размещения требуется доказать, что сохранены нулевые байты профиля, а выбранные запуск, останов, служебный режим, обновление ПО и восстановление CAN не дают других записей или переотображений в окно. При входе в режим, в котором владение RAM меняется, выходы сначала остаются независимо заблокированными. На повторном захвате области её состояние инициализируется заново. Статический вывод для конкретной ветви H03 и тесты её конфигурации позволяют продолжить проверку кандидата, но пока не дают основания назначить его целевой сборке.

### Прочие записи в RAM

| Источник | Диапазон и доказательство |
| --- | --- |
| DMA0, DMA1 | `0x00AAEE/AB0C` задают адреса `0x806ACE/806ADA`. `0x00AB78/AB84` повторно записывают те же адреса. `DMxTCT=5`, управляющее слово после разрешения `0x79`. В обычном режиме канал делает шесть 16-битных переносов с увеличением адреса назначения. Оба массива вместе занимают `[0x806ACE,0x806AE6)` |
| DMA3 | `0x00CEE4` задаёт `0x800113`, вход данных SIO0 для передачи. Управление `0x5E` сохраняет адрес назначения фиксированным |
| DMA4 | `0x00CF50` получает младшее полуслово адреса из аргумента. В исходной таблице `0x032768` указатель ведёт на `0x00CF0C`. Прослеженные вызовы `0x00DD38`, `0x00DE0E`, `0x00E93E` используют служебные приёмники начиная с `0x80683A` или `0x80683B` для проверенного канала 0. `0x6D` означает 8-битные переносы с повышением адреса в обычном режиме. С консервативным пределом 256 переносов конечная граница назначения не превосходит `0x80693B` |
| DMA2 и DMA5–9 | Скан прямых загрузок и выровненных литералов адресов каналов не выявил настройки назначения. Вывод ограничен разобранной адресацией. [Renesas 32176, §§ 9.2.3–9.2.5][dma] |

Есть отдельный монитор загрузчика. Его вход `0x0034A0–0x0034B4` проверяет ROM `0x000201`. В точном H03 там `01`, поэтому низкоуровневый путь монитора остаётся в разрешённой конфигурации. В `0x002978` монитор пишет в область по рабочему указателю. Ограничение перед записью в `0x003528–0x003546` защищает собственный участок монитора около `[0x808578,0x808DB4)`; кандидат расположен ниже и этой проверкой не защищён. Второй путь `0x002DE0` использует рассчитанный адрес назначения и счётчик. Ему предшествует ветвь `0x003608 → 0x0035F4 → 0x002D1C` штатного ADC0 IRQ. Это отдельные пути по отношению к отключённому диспетчеру `0x00D574`. Их сосуществование со штатным приложением зависит от состояния сеанса и обслуживающих условий. Вывод о свободной RAM из одного условия `0x03001B/1C = 00/00` исключён.

Для целевого допуска требуется подтвердить, что обслуживающие пути монитора и проектный контроллер не владеют одним диапазоном одновременно. Условие проверяется до перехода в сервис, независимо от вызовов фаз 3/2, и на возврате из него. Проверка прямых адресов и DMA оставляет окно кандидатом для дальнейшей работы. Она не устанавливает полное покрытие всех сервисных состояний.

## Стек и рабочие объекты

В H03 активен `CR2/SPI` с началом `0x809EFC`. Общий IRQ-пролог `0x003DE0–0x003E02` сохраняет 12 слов, 48 байт, на том же стеке. Чтение `IVECT` устанавливает новый порог приоритета. Диспетчер включает прерывания перед вызовом обработчика. По правилам 32176 и настройке H03 `0x009B06–0x009B9E` семь уровней `0…6` дают верхнюю границу в 336 байт только для совместно живущих общих кадров маскируемых прерываний. К ней прибавляются живые кадры конкретных обработчиков. Ветка SBI `0x000010 → 0x003F50` добавляет 40 байт на SPI и одну 4-байтную запись в отдельном стеке PSW через `0x003E50`. Указатель последнего хранится в `0x809F9C`, новые записи занимают меньшие адреса. Оба нижних предела требуют проверки. [Renesas 32176, обработка EIT и прерываний, §§ 4 и 5.2][interrupts] · [M32R Software Manual, регистры CR2 и CR3][m32r]

### Разобранные пути прерываний

Аудит читает двухуровневые указатели векторов и разворачивает фиксированные таблицы вызовов штатного H03. Для общих обработчиков CAN учтены 34 позиции перехода `0x002EDA`. Пути для ADC0 используют четыре указателя, инициализированные в `0x003934–0x003960`. Для рассматриваемой конфигурации штатных таблиц аудит закрыл косвенные рёбра в обработчиках прерываний. Динамическая подмена таблиц и изменения приоритетов за условиями модели требуют отдельной проверки.

| ILEVEL | Обработчик, задающий максимальный локальный расход | Байты сверх общих 48 |
| --- | --- | ---: |
| 0 | TOP8/9 `0x00ACD8` | 20 |
| 1 | CAN0 `0x004724`, TOP10 `0x0046EC` достигает 92 | 96 |
| 2 | TIO8/9 `0x00C0A0` | 52 / 92 / 132 |
| 3 | DMA0–4 `0x00AB44` | 16 |
| 4 | TIN20–23 `0x00A9EC` | 16 |
| 5 | CAN1 `0x001C04` | 92 |
| 6 | ADC0 `0x003608` | 76 |

Три значения для TIO8/9 соответствуют 0, 1 и 2 дополнительным вызовам `0x00B800`. Цепочка `0x008324 → 0x008400 → 0x00B800 → 0x00BAF4 → 0x008324` повторяется по условию изменения пары указателей в режиме 4. При устойчивом режиме 4 настройка пары идемпотентна. TOP10 с более высоким приоритетом может сменить режим в `0x008F2C` между чтениями. Для одного штатного перехода в режим 4 и стабильных остальных полей модель допускает два дополнительных вызова. Предел зависит от сохранённой конфигурации и отсутствия параллельного изменения этих полей сервисным монитором.

По сумме максимумов семи уровней и 336 байт общей рамки бюджет составляет 704, 744 или 784 байта. С SBI соответственно 744, 784 или 824 байта. Аудит даёт 68 байт внутри штатной фазы 2, 180 байт внутри штатной фазы 3 и 204 байта на одном разобранном пути от reset. Для этого пути сложение `204 + 824` даёт `SPI=0x809AF8`. Это условная оценка для разобранной цепочки. Она исключает неопределённые вложенные вызовы других ветвей foreground, вызовы из RAM `0x805000/0x8051E8` и новое приложение Toyota. Нижняя граница всего SPI из этого расчёта не следует.

Отдельный стек PSW разворачивает запись вниз от `0x809F9C` в `0x003E50–0x003E62`. `0x003E70` восстанавливает CR0 до публикации поднятого курсора в `0x003E72`. Если восстановлено разрешение прерываний, при оценке глубины следует учитывать это окно между двумя инструкциями. Измерение SPI отдельного от этого объёма не покрывает курсор PSW. [Проверка штатных IRQ](../targets/lfj8/audit_h03_irq_stack.py)

При вызове исходного расчёта Toyota через стратегию по `0x036F30` от reset остаётся 36 байт штатных кадров. Обёртка добавляет 72 байта. Бюджет из этих 108 байт, четырёх разобранных кадров исходного API (1116 байт) и 824 байт IRQ/SBI составляет 2048 байт ещё до кадра адаптера и дальнейших вызовов. При начальном SPI `0x809EFC` это соответствует `0x8096FC`. Предполагаемый участок `[0x809700,0x809EFC)` вмещает 2044 байта. Сумма использует расчётную модель вложения. Предполагаемая граница участка требует отдельного подтверждения. [Обёртка H03](../targets/lfj8/h03_native_hooks.S)

Предварительный агрегат из `RbmU340eRuntime`, takeover, двух трекеров захвата S51/S83, CAN RX, контроля диапазона, ATF, наблюдателя передачи, АЦП селектора, CAN TX, состояния драйвера и планировщика занимал 1080 байт. Отдельный снимок пары захватов поднимал его размер до 1116 байт. Этот расчёт предшествует добавлению общего цикла, клиента момента и диагностических состояний. Он показывает, что 360-байтное рабочее представление передач, а затем и общий буфер 564 байта требуют отдельного места.

## Проверка полного программного цикла Toyota

Временная копия GP хранится в буфере вызывающего кода. После завершения расчёта передач память `FactoryGearState` переиспользуется для транзакции `FactoryHydraulics`. Объединение типов занимает 564 байта в ABI M32R. При успешном расчёте копия публикуется целиком. При отказе активный GP сохраняется. На M32R побайтно совпали результаты для 269 рабочих проходов из тестов Toyota. Дополнительный проход проверил откат при отказе вычислителя момента после успешной стадии гидравлики. [Код транзакции](../controller/hydraulic_port.py) · [Контракт](../controller/include/rbm_u340e_hydraulic_workspace.h)

| Вход в расчёт | Максимальная глубина изменённых слов пробного стека |
| --- | ---: |
| Исходный `factory_hydraulics_control_main` | 1220 байт |
| Гидравлика и момент с внешним буфером | 660 байт |
| Расчёт передач и логических выходов | 596 байт |
| `lfj8_h03_cycle_tick` с внешним буфером | 704 байта |

В последней строке проверены 4302 вызова, включая P/N→D, переключение 1→2, переход счётчика через ноль и потерю события. Пробник сохранял исходные SPI и SPU, переключался в SPU только на время измеряемого вызова и сверял 32 байта защиты с каждого края. Сценарии исполнялись без моделирования вложенных прерываний. Самая глубокая изменённая ячейка показывает наблюдаемую глубину записи. Для точного максимума SPI также учитываются инструкции, которые резервируют место без записи, реальная точка вызова и аппаратура. [Отчёт M32R](../verification/e4m3-can-9e1c/h03-toyota-stack.json)

Сумма 704 байт цикла, 108 байт штатных кадров и обёртки и 824 байт из отдельного аудита IRQ/SBI даёт 1636 байт до размещения кадра адаптера. В условном окне 2044 байта остаётся 408 байт до дополнительных расходов. Длина основного состояния цикла равна 32 байтам. Снимок входа и результат занимают ещё 20 и 28 байт соответственно. Для целевой карты состояния нужно учитывать отдельные буферы связи и оставшиеся участки с неизвестным максимальным стеком.

Для буфера в 564 байта проверено второе окно `[0x808E40,0x809074)` после участка сброса. Скан исходного H03 не нашёл фиксированных ссылок из проверенных классов. Во всех шести испытаниях штатной инициализации область сохранила контрольные байты. Владение при косвенных сервисных записях, всех источниках DMA и всех режимах работы H03 зависит от устройства. Для выпуска требуются окончательная карта, нижняя граница SPI и аппаратная проверка вложенных IRQ. [Отчёт по RAM](../verification/e4m3-can-9e1c/h03-ram-candidate.json)

## Воспроизводимые проверки

```powershell
python -B targets/lfj8/check_h03_ram_init.py --base $base --gcc $m32r
python -B targets/lfj8/check_h03_ram_candidate.py --base $base --gcc $m32r
python -B targets/lfj8/check_h03_storage.py --base $base --gcc $m32r --out local/h03-storage.json
python -B targets/lfj8/audit_h03_irq_stack.py --base $base --gcc $m32r
python -B controller/build_target.py m32r --cc $m32r --out local/stack-check
python -B targets/lfj8/check_h03_toyota_stack.py --base $base --gcc $m32r --controller local/stack-check/rbm_u340e_m32r_be.o
```

Вторая проверка сначала сверяет SHA-256, затем исполняет шесть изолированных неизменённых фрагментов OEM на симуляторе M32R. Каждый прогон сравнивает все 24 576 байт. Проверены очистка RAM приложения, CAN-записи, конфигурация DMA0/1, условная очистка конфигурации, проверка профиля сервисного диспетчера и заполнение служебного массива. Во всех шести случаях кандидат сохранил исходные байты; трассы за пределами этих фрагментов требуют отдельной проверки. [Скрипт аудита](../targets/lfj8/check_h03_ram_candidate.py)
