# Расчётный контроллер U340E

Модуль `controller/` содержит переносимый C11-слой RB Motors и зафиксированные исходники расчётного ядра Toyota. Источник ядра — согласованный `CM-AVEO-TCM-AKP-U340`, коммит `8cf4308d8539253d4ac994dd99c9650f02da6236`. Реестр в `controller/vendor/toyota/manifest.json` фиксирует Git blob SHA и SHA-256 31 файла. Сборка проверяет эти SHA-256. Генератор `hydraulic_port.py` адаптирует только передачу данных между каноническим буфером GP и структурами C. Алгоритмы и исходные файлы Toyota сохранены по зафиксированной ревизии. [Зафиксированный каталог ядра](https://github.com/almirpangor/CM-AVEO-TCM-AKP-U340/tree/8cf4308d8539253d4ac994dd99c9650f02da6236/firmware/tcm/toyota-u340e/source-u340e/factory)

## Интерфейс

| Вызов | Входы | Результат |
| --- | --- | --- |
| `rbm_u340e_init` | Начальный режим, начальное состояние OD, разрешённые положения селектора для Tiptronic, режимы, в которых OD Off исключает 4-ю передачу | Состояние контроллера. Параметры политики задаёт интегратор. |
| `rbm_u340e_step` | Стабилизированные кнопки с признаком достоверности, декодированный селектор, подтверждённая текущая передача, актуальная маска разрешённых передач, состояние переключения, согласованный снимок Toyota `FactoryRequestState` для Auto | Логическая пара команд реле, состояние Auto/Tiptronic и OD, признак одного нажатия OD, флаг конфликта кнопок, разрешённый логический запрос передачи 1–4 или 0, обновлённое состояние запроса Toyota. |
| `rbm_u340e_outputs_init` | Подтверждённое логическое состояние автоматов драйверов Toyota для каналов 0, 1 и 5 | Рабочая копия состояния выходов. |
| `rbm_u340e_outputs_step` | Подтверждённый снимок Toyota для S1/S2, ST, SLT и состояния драйверов в донорских единицах | Упорядоченный список логических записей S1/S2/ST, расчётный запрос и характеристика SLT, обновлённые состояния. Неуспешный шаг обнуляет результат и сохраняет прежнее состояние драйвера. |

В Auto процедура `factory_request_stage` вычисляет индекс по заводским банкам порогов, включая специальные ветви Toyota. Выход подтверждается внешней маской допустимых передач. В Tiptronic одиночный фронт «+»/«−» относительно подтверждённой передачи формирует запрос на соседнюю. Удержание, одновременные фронты противоположных команд и запросы во время уже идущего переключения обработаны программно. После восстановления качества входных данных первое состояние кнопок запоминается, чтобы удерживаемая кнопка не создавала команду. Политика OD может исключать 4-ю в Auto или Tiptronic. Первый запуск и сохранение режима при выключении питания подлежат согласованию по ТЗ.

Выходной шаг использует функции Toyota `factory_shift_outputs`, `factory_st_output`, `factory_driver_dispatch` и `factory_slt_correction_step`. Команды рассчитываются по согласованному снимку гидравлической задачи. Адаптер платформы должен передать статусы каналов, состояние фазы и её счётчики. Расчётные функции давления, гидравлики, обучения и сохранения адаптаций доступны из ядра через соответствующие заголовки. Подключение NVM и привязка его циклов к условиям прошивки входят в аппаратный слой.

## События задач Toyota

`rbm_u340e_scheduler` воспроизводит границы задач Toyota по доставленным событиям. `finish_init` снимает запрет после завершения внешнего INIT. В доноре IRQ `013F96` увеличивает `GP−3296` до проверки допуска, затем активирует задачу 2 через `013FBE`. У задачи 2 шаг публикации и завершение разделены. Повторный IRQ, пока задача 2 занята, фиксирует останов планирования по ветви `01413A → 014164`. Операции над состоянием вызывает один владелец. [Интерфейс планировщика](../controller/include/rbm_u340e_scheduler.h) · [Модель событий и проверка по коду Toyota](https://github.com/almirpangor/Chery-TA2005-U340E/blob/08c01a012737ed0ef5203d67133ec76b75df333b/docs/SCHEDULER_EVENT_MODEL_RU.md)

| Граница Toyota | Условие и переход |
| --- | --- |
| Задача 2, `014484` | До увеличения `GP−9490` фазы 2 и 6 по модулю 8 публикуют FAST. Фаза 4 активирует SECONDARY. |
| FAST, `014520 → 05425C` | Захват очищает ожидающий бит. Повторная публикация до захвата сливается. Новый бит после захвата ждёт следующего прохода, даже если прежний FAST ещё выполняется. |
| SECONDARY, `01455C → 05421C` | Повторная активация занятой задачи отбрасывается. После SECONDARY на чётном `GP−9486` следует MAIN `0540E4`. Счётчик продвигается при завершении всей задачи 22. |

В начале FAST сохраняется исходный `GP+1060` и обновляются восемь банков из 197 насыщающихся счётчиков `GP−4816…−4620`. Завершение в `054346/054348` сохраняет исходную фазу плюс один с переполнением байта. Тест подменяет фазу в теле задачи с 255 на 17 и подтверждает запись 0 на выходе. Счётчик завершений оболочки FAST продвигается отдельно после возврата. [Исходная граница банков FAST](https://github.com/almirpangor/Chery-TA2005-U340E/blob/08c01a012737ed0ef5203d67133ec76b75df333b/docs/C167_FAST_COUNTER_PREFIX_RU.md)

При своевременном выполнении 16 событий задачи 2 дают четыре FAST, два SECONDARY и один MAIN. Частоту события, приоритеты целевого исполнения и недостающие тела стадий задаёт интеграция. Например, `factory_hydraulics_load_observer` относится к FAST-вызову `0542FA → 054B34` после `0542F6 → 054EB2`. Пара `05A988 → 05AD5E` выполняется позже в `054312/054316`. Их порядок сохраняется через границы владельца задачи. Модуль пока вызывает численный префикс банков и завершение FAST. [Тесты границ и переполнений](../controller/tests/test_runtime.c)

### Квалификация нагрузки в SECONDARY

Вызов `054220 → 05518C` выдаёт `GP+1120` перед использованием в MAIN. Для первичного и ограниченного запросов вход в область малой нагрузки происходит при значении ниже 80. Снятие происходит при достижении 80 плюс интерполированное значение из ROM `000D64`, сдвинутое вправо на четыре. Исходный порог зависит от `GP−7186`. При `GP−5299.1 = 1` оба расчёта получают штатное значение 786. Бит `GP−5250.2` дополнительно удерживает только третий запрос. Подтверждённые биты `.1/.3/.5` меняются при повторении предварительных битов `.0/.2/.4` на двух выполнениях. [Реализация](../controller/src/rbm_u340e_runtime.c) · [Сверка R2 с V850](https://github.com/almirpangor/Chery-TA2005-U340E/blob/7585de6945b4b6b3ef381c6062070a5f417cf588/research/results/C167_SECONDARY_LOAD_QUALIFIER_PROBE.json)

В тестах ПК и M32R переход P/N→D получает `GP+1120` из SECONDARY. При использованных нагрузках после первого вызова получается `0x11`, после второго — `0x33`. В 8 192 сравнениях с исходными инструкциями S01 V850 проверены 186 адресов инструкций, включая обе ветви нагрузки и интерполяцию. Ещё 65 536 сравнений с отдельной реализацией R2 покрывают все пары прежних значений `GP+1120` и значений `GP−5250`. [Переход диапазона и регрессии](../controller/tests/test_runtime.c) · [Эталон R2](https://github.com/almirpangor/Chery-TA2005-U340E/blob/7585de6945b4b6b3ef381c6062070a5f417cf588/toyota_isolation/load_qualifier.c)

Подключение к H03 требует пригодных донорских величин нагрузки. В S01 `GP−5250.2` формируется в `02CDBC…02CE4A` из `GP−5266` с учётом `GP−5265` и `GP−5188.2`. `GP−5266` связан с собственной машиной состояний двигателя по `GP−9022/−9024`. Для `GP−5722` непосредственные источники в `02760E` — `GP−5471.4`, инвертированный `GP−5471.1` и `GP−5471.0` для битов 1–3. Бит 0 обновляется из `GP−5483.5` под условием штатной ветви `0277AC…0277DE`. В модели тестовые значения этих сигналов заданы явно. Для физического H03 соответствующие источники ещё требуется подтвердить. [Аудит границ GP](https://github.com/almirpangor/Chery-TA2005-U340E/blob/7585de6945b4b6b3ef381c6062070a5f417cf588/research/results/TOYOTA_BOUNDARY_EVIDENCE.txt)

Для повторения 8 192 сравнений нужны исходный S01, библиотека текущего контроллера и проверенный листинг V850. При локальной проверке использован файл `rbm-05518c-v850-listing.txt` в каталоге `$env:TEMP`. Он охватывает вход `054220` и вызываемые участки `05518C`, `054CA6`, `054C2C`, `012F9C`. ## Сборка и проверки

Из корня проекта выполнить команду, указав установленный Zig. Текущая проверка Windows выполнена на Zig 0.13.0.

```powershell
python controller/build.py --cc "C:\path\to\zig.exe"
```

Команда проверяет происхождение импортированных исходников, собирает динамическую библиотеку и тестовую программу, выполняет тесты и записывает результаты и SHA-256 в `local/controller/manifest.json`. На Windows выходы называются `rbm_u340e.dll` и `u340e_controller_test.exe`. Для программной интеграции нужны `controller/include` и `controller/vendor/toyota/include`.

### Big-endian сборки

```powershell
python controller/build_target.py m32r --cc "C:\path\to\m32r-elf-gcc.exe"
python controller/build_target.py sh2 --cc "C:\path\to\sh-elf-gcc.exe"
```

Гидравлическое состояние хранится в 561 байте канонического little-endian буфера GP. При чтении и записи на big-endian цели переводится порядок байтов каждого отдельного поля и элемента массива. Однобайтовые поля и порядок элементов массива сохраняются, в том числе при захвате адаптаций. Размер каждого поля C проверяется при компиляции.

`RbmU340eRuntime` занимает 829 байт вместо 928. В каноническом GP хранятся 93 общих байта, а отдельное поле содержит 267 байт частного состояния передач. Для расчёта типизированный снимок из обоих источников собирается в отдельно выровненном `FactoryGearState` размером 360 байт. Пересечение этого рабочего объекта с постоянным состоянием или пакетом команд отклоняется. Изменение раскладки требует пересборки всех C-модулей, выделяющих `RbmU340eRuntime`. [Интерфейс состояния](../controller/include/rbm_u340e_runtime.h) · [Тесты проекции и пересечения буферов](../controller/tests/test_runtime.c)

| Среда | Фактический результат |
| --- | --- |
| Windows x86-64, Zig 0.13.0 | Проверены все 292 поля девяти карт преобразования и пять последовательных снимков расчёта. Хеши всех 561 байта совпали с неизменённой сборкой R1. Прошли проверки логических выходов, общего GP и планирования. |
| M32R big-endian, GCC 4.8.0 | Получены объект `rbm_u340e_m32r_be.o` и тестовый `u340e_m32r_sim.elf`. GNU M32R Simulator исполнил тот же набор проверок, включая числовые значения, обратную запись GP и переходы планирования. |
| SuperH SH-2 big-endian, GCC 8.4.0 | Получен `rbm_u340e_sh2_be.o` в формате ELF32 REL с `e_flags=0x2`. Целочисленная сборка `-m2 -mb` выполнена в двух тестах. `u340e_sh2_sim.elf` выполнился за 351 914 шагов с пиком стека 2 412 байт. Проверка уплотнённого состояния, общего GP и планирования в `u340e_sh2_runtime_sim.elf` заняла 799 612 шагов с пиком 3 952 байта. Оба теста вернули 0 и восстановили SP и R8–R14. |

Объекты и манифесты версий и SHA-256 записываются в `local/controller/m32r` и `local/controller/sh2`. Для M32R используется программа `m32r-elf-run` из комплекта GCC. Для тестов SuperH нужно собрать программу из `targets/pcm-s05/native/check_sh` и передать её путь параметром `--sh-runner` к команде `build_target.py sh2`. Текущий предел в миллион шагов покрывает оба теста. [GNU M32R GCC для Windows](https://gnutoolchains.com/m32r/) · [Windows SH GCC в Jo Engine v2026.5](https://github.com/johannes-fetz/joengine/tree/v2026.5/Compiler/WINDOWS)

Статические размеры отдельных стековых кадров SH-2 собраны в `local/controller/sh2/stack-usage.tsv`. Например, `factory_hydraulics_control_main` выделяет 576 байт, вызываемая `main_step` — 220 байт, а `factory_phase_modes_step` — 200 байт. Эти размеры используют для расчёта полного дерева вызовов вместе с пиком прерываний. Пики тестов включают размещённые на стеке проверочные состояния и снимки. У штатного task S05 выделено 2 048 байт. Для компоновки требуется отдельный бюджет рабочего стека. [Границы интеграции S05](pcm-s05-integration.md)

## Привязка к LFJ8

### Обороты и температура охлаждающей жидкости

`rbm_u340e_runtime_prepare_engine` принимает согласованные `FA62/F9B8/E026/FD10` после квалификации TA2005 `06E856` и `06ED70`. Снимок формирует операнды `GP−9306 = floor(FA62 × 4/25)` и `GP−9006 = floor(max(F9B8 − 10, 0) × 8/5) − 64`. Признак `E026.1` замещает операнд оборотов нулём. `GP−8677.4` устанавливается при `FD10.12` или `F9B8 = FF`. Семь других битов `GP−8677` сохраняются. [Квалифицированный вход TA2005](https://github.com/almirpangor/Chery-TA2005-U340E/blob/08c01a012737ed0ef5203d67133ec76b75df333b/docs/TA2005_QUALIFIED_ENGINE_FEED_RU.md)

После подготовки значения публикуются в отдельных точках MAIN. В `0540F4 → 055336` `rbm_u340e_runtime_main_coolant` вычисляет `GP−7164` со штатной подстановкой 30720. В `054110 → 054D6A` `rbm_u340e_runtime_main_engine_speed` записывает младшие 16 бит удвоенного `GP−9306` в `GP−7186`. В программном тесте для 1200 об/мин и 87 °C получены коды 3072 и 32480. Квалификацию актуальности, порядок промежуточных вызовов и разрешение силовых выходов ведёт владелец MAIN. [Интерфейс](../controller/include/rbm_u340e_runtime.h) · [Проверка этапов публикации](../controller/tests/test_runtime.c)

H03 выдаёт `FAD8/F9E9` по CAN `0x0FA/0x278` с раздельной свежестью. Вызов `ta2005_engine_qualifier_task2` преобразует снимок в `RbmU340eQualifiedEngineFeed` и хранит шесть байт состояния. Флаг доступности каждого канала берётся из снимка CAN. При отсутствии свежего значения используются исходные признаки `FFFF/FF`. Подтверждение отказа наступает через 102 вызова для RPM и 202 для ОЖ. Снятие каждого отказа требует 252 подходящих вызова. После потери шины по маске `E02B & 84h` обороты обнуляются, выбирается резерв ОЖ, оба счётчика и обе защёлки сохраняются. Возвращаемые события указывают на новые DTC с индексами `15h` и `14h`. Ведение диагностической истории остаётся задачей вызывающего кода. [Интерфейс](../targets/lfj8/ta2005_engine_qualifier.h) · [Квалификация каналов TA2005](https://github.com/almirpangor/Chery-TA2005-U340E/blob/7585de6945b4b6b3ef381c6062070a5f417cf588/docs/TA2005_CHERY_QUALIFIER_RU.md)

В сравнении с инструкциями S03 прошли 9 217 отдельных снимков и 1 566 шагов восстановления и отказов на ПК и в симуляторе M32R. Отдельный тест проверил переход счётчика времени через ноль и независимое устаревание CAN-кадров. Период задачи 2, источник состояния шины и резерв `FA7B` задаёт вызывающий слой. При отсутствии подтверждённого резерва передаётся `FF` и Toyota применяет код 30 720 через свою ветвь замещения. [Отчёт сравнения](../verification/e4m3-can-9e1c/ta2005-engine-qualifier.json) · [Сценарии приёма, отказа и восстановления](../targets/lfj8/test_ta2005_engine_qualifier.c)

`lfj8_h03_engine_feed_task2` связывает приёмник H03, численную квалификацию и общую запись сканера. Обычный тайм-аут кадра сохраняет донорские задержки. При переинициализации приёмника, утрате владения или остановке тактов накопленные RPM перестают выдаваться, а счётчики отказов приостанавливаются до восстановления приёма. Потеря, замеченная между вызовами квалификации, учитывается один раз даже при уже восстановленных CAN-объектах. Подтверждённые отказы RPM и ОЖ появляются как U111F/U1100, при восстановлении сохраняется их историческая запись. Успешная команда `14 FF 00` сбрасывает счётчики и принадлежащие квалификатору флаги однократно, в том числе при недействительном времени. Проверка исходного цикла S03 `0652FC–065312` подтвердила сброс счётчиков, защёлок и `E026` с сохранением `FA62` и признака температуры в `FD16.2`. У владельца рабочего цикла остаются физическая частота вызова, инициализация CAN и отдельное разрешение силовых выходов. [Сценарий связанного приёма](../targets/lfj8/test_lfj8_h03_engine_feed.c)

Для расчёта нагрузки в `054100 → 054AB2` нужны знаковые результаты арбитража `GP−8270/−8272`, ограничители `GP−8306/−8298/−8302/−8310`, разность `GP−9044−GP−9030` и признак `GP−5299.1`. Производители используют фильтрованный двухканальный дроссель и вычитание обученного нуля, ограничитель `GP−9046` и два выхода `033AE0` с отдельными режимными картами. Для GW остаётся подтвердить соответствие `GP−9046/−8288/−8330` на переходах. При одинаковом TPS проверка Toyota получила разные команды давления после изменения одной только поправки. [Граница сигналов нагрузки GW и Toyota](https://github.com/almirpangor/Chery-TA2005-U340E/blob/08c01a012737ed0ef5203d67133ec76b75df333b/docs/GW_TOYOTA_LOAD_SIGNAL_BOUNDARY_RU.md)

У S01 три бита `GP−5722.1/.2/.3` идут от фильтра группы 2 локального периферийного обмена. Таблица `00309C` выбирает запрос `4400`, затем `01E434–01E49A` проверяет маску ответа и обновляет `GP−5471` с учётом двух последовательных состояний. Бит `.0` идёт от отдельного ответа через `01DEF0–01DF28` и дополнительные условия. Штатная проверка P0705 сравнивает `.2` с положением P/N. Одного положения резистивного селектора недостаточно для такого сравнения. Сигналы LFJ8, которые заменят эти квалификаторы, требуется подтвердить отдельно. [Карта входов](lfj8-h03-input-paths.md) · [Стендовый протокол](lfj8-9e1c-minimum-bench.md)

### Остальные условия интеграции

Для SLU отдельно сверена переносимая функция Toyota `055C5E` из R3. Проверены все 65 536 входных слов по характеристике из S01, порядок записи управляющих регистров, форсирование и возврат в два состояния драйвера. Проверка моделирует регистры Toyota. Цепь от снимка входов H03 до расчёта SLU, назначение канала силового блока и его электрические характеристики остаются открытыми. [Результат проверки](../verification/e4m3-can-9e1c/toyota-slu-host.json) · [Воспроизведение](../targets/lfj8/check_toyota_slu.py)

- Слой ввода LFJ8 определяет достоверность селектора, кнопок, VSS, NT, ATF и CAN. Он выполняет подтверждённое преобразование параметров в донорские шкалы. Передача 4 и смена передачи в Tiptronic разрешаются по проверенным ограничениям конкретной АКПП.
- Событийные границы Toyota реализованы. Для LFJ8 требуются целевой период и порядок приоритетов, полные тела задач, состояние гидравлики для переходов, команда SLU и согласование момента со штатным CAN Chery. Численные функции принимают состояние, сформированное этими стадиями.
- Драйвер LFJ8 должен переводить логические команды в подтверждённые контакты, уровни, токи и длительности, обеспечивать аппаратную защиту, обработку пропадания данных и отказобезопасное состояние выходов. Диагностика LFJ8 и её интеграция со сканером Chery проверяются на отдельном стенде.
- При компоновке SuperH нужны функции GCC для сдвигов и деления, `memcpy` и `memset`. Ядро собрано без FPU-инструкций. Для вызова из штатного ПО S05 требуются проверка ABI, учёт сохранения контекста FPU планировщиком и подтверждение места размещения кода и данных.
