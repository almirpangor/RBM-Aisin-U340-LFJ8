# DTC-02 — штатный приём BasicCAN RX14/15 на H03

Проверка от 20.11.2026 на базе `a52ab8ce955959ed109d53e6c554beb68f814c2e`.
M32R исполняет оригинальные инструкции H03 от входа `0x0013F0` до возврата.
Исходник `LFJ8-T-D.bin` сверяется по размеру и SHA-256 из реестра H03.
Образ с другим SHA-256 отклоняется до запуска.
[Сценарии и точки наблюдения](../../targets/lfj8/check_h03_dtc_basiccan.py)

```powershell
python -B targets/lfj8/check_h03_dtc_basiccan.py --base $h03 --gcc $m32rGcc --out local/audit/h03-dtc-basiccan.json
```

## Результаты M32R

Все 15 сценариев прошли. Проверка сопоставляет последовательность наблюдений, все 16 байт каждой копии, возврат, баланс стека и сохранение R8–R10.

| Сценарий | Наблюдение |
| --- | --- |
| Один или оба RX-слота | При двух заявках H03 сначала обслуживает RX15, затем RX14. Сценарии `0x732` сохраняют DLC 8 и DLC 3 и метки `0x1234` и `0x1300` соответственно. |
| Нет заявки | Обработчик возвращается, не читая слот. |
| Заявка без TRFIN | При MSC `0x40` OEM всё равно копирует слот. Будущий диагностический наблюдатель должен проверять исходный TRFIN, чтобы остаточная заявка не породила повторную доставку. |
| Подмена слота в середине копии | На первом проходе в копии смешаны байты двух кадров, а MSC равен `0x41`. Ветка по `0x001570` возвращается к `0x001534`. Точка `0x001574` достигается один раз, уже после полной повторной копии. |
| Подмена после чтения MSC, до записи | `0x001540` читает `0x41` для старого кадра. После подмены регистр в модели содержит `0x45`, но `0x001544` пишет `0x40` из старого значения. OEM проходит проверку TRFIN с новым содержимым и без наблюдённого ML. |
| Ложные входы | Проверены `0x733`, установленный ML, RA и расширенный формат. OEM доходит до стабильной копии, но кадры этих сценариев не совпадают со штатными ключами. Условия пригодности для проектной очереди остаются в существующем декодере. |
| Штатный сервис | `0x7E1` и `0x7DF` поступают в `0x003830`. `0x602` с DLC 8 копируется в `0x808DFC` и достигает вызова штатного монитора по `0x0034B4`. Для `0x602` с DLC 3 монитор не вызывается. |

В обоих сценариях подмены к моменту возврата остаётся новая заявка RX15 в тени CAN0SLIST. Проверка с отдельной заявкой без TRFIN показывает, почему одного бита CAN0SLIST для выдачи диагностического кадра недостаточно.

Два одинаковых прогона на Windows выдали JSON с SHA-256
`7808c23441bea2ade195e13f3de45d5035525a20908577ff9a2f6b9d58a5aa6f`.
Ниже события сценария подмены между чтением MSC и очисткой TRFIN. Числа записаны в hex, `f` обозначает RX15.

```text
pre_clear f 41 0
overwrite f
write_msc f 40
copy f 40 1c 32 ad be ef 3 30 0 0 cc cc cc cc cc 13 0
stable f
```

## Открытые проверки

**Программная интеграция.** Согласовать точку привязки с ограничением приложения `0x008000`. Копирование и выбор OEM-маршрута находятся ниже этой границы. Привязка должна сохранить штатный путь и проверять MSC до и после копирования, включая потерю, отсутствие исходного TRFIN и незавершённую запись. Для проверки ML документация Renesas рекомендует команду `0x4E` при снятии TRFIN. Штатная операция чтение–маска–запись в показанном окне даёт `0x40`. Подключение очереди к foreground и к поколению владельца CAN остаётся отдельной частью DTC-02. [Renesas 32176, §13.6.3](https://www.renesas.com/en/document/mah/32176-group-hardware-manual#page=553)

**Оборудование.** Регистры CAN представлены тенями в RAM. Стендовая проверка ML, фактических моментов установки TRFIN и CAN0SLIST, приёма через трансивер и интервалов IRQ открыта. Подмена кадров привязана к инструкциям в GDB и не измеряет длительность окна. Сценарии не исполняют запись Flash. Проверка проводилась с локальным исходным H03 и временным ELF симулятора.
