# MODE-02 — восстановление после конфликта кнопок Tiptronic H03

Основа — опубликованная `main` `f64eff7c24744cef0fe608415039c6d10c677ff1` и сданный захват MODE-02 `5d793be878e4b3732133535f3255609bc7c44dd3`. Основа H03 для проверок — `LFJ8-T-D.bin`, SHA-256 `844a11b809cda1f2ccaf90cb6a75666009487ccedd2e8190b7eb46137b855544`.

## Путь запроса

Захват AN2/P1DATA обновляет фильтр через `lfj8_h03_input_capture` и `lfj8_range_control_sample_buttons`. После квалифицированного одновременного нажатия «+» и «−» фильтр сохраняет конфликт, пока обе кнопки не пройдут существующий фильтр отпускания. Кнопка, остающаяся нажатой при частичном отпускании, не образует нового фронта при очередном вызове `lfj8_h03_input_capture_toyota`. Уже удерживаемая ручная цель снимается штатной обработкой конфликта.

Квалифицированное отпускание сбрасывает только фронты двух кнопок переключения. Следующее самостоятельное нажатие можно принять, даже если между отпусканием и новым нажатием не было события Toyota. Потеря входа по-прежнему снимает допуск кнопок. [Фильтр](../../targets/lfj8/lfj8_range_control.c) · [Привязка захвата](../../targets/lfj8/lfj8_h03_input_binding.c)

## Проверка

- ПК, Zig 0.13.0. Новый сценарий `test_lfj8_h03_input_binding.c` воспроизвёл потерю признака конфликта на `5d793be`. С исправлением весь тест адаптера прошёл.
- Общий прогон ПК прошёл 41 шаг, включая сквозную модель `PASS_OFFLINE_ONLY`. В Python прошло 178 из 179 тестов, один пропущен без `RBM_S03`. Отдельным повтором с закреплённым EMS-S03 прошли оба теста таблицы DTC, включая пропущенный.
- M32R, GCC 4.8.0. Пересобраны контроллер и мост для указанного H03. `check_h03_toyota_source.py` прошёл сценарий с TML0, AN2/P1DATA и реальным адаптером входов. Конфликт возник и частично разрешился между двумя событиями Toyota, прежний запрос 2→3 был снят. Дребезг при отпускании не дал 2→1. После подтверждённого отпускания новый «−» дал ровно один запрос 2→1. [Сценарий](../../targets/lfj8/test_lfj8_h03_toyota_source.c)
- `check_integrated_h03.py --suite components` прошёл 8 групп. `check_h03_image_layout.py --profile padding-candidate --cpu-test` прошёл 6 групп исполнения размещённого ядра. Адресный результат ядра — `PASS_ADDRESS_MODEL_ONLY`.
- Стандартный `check_h03_link.py` повторил известный отказ `main`: компактный набор не удерживает `rbm_u340e_runtime_prepare_s01_cold`. С локальным добавлением этого корня в `H03_ROOTS` прошли 11 интеграционных и 18 компонентных проверок с закреплённой трассой Bosch. Сборщик в репозитории не менялся.
- `project_status.py --check` помечает семь файлов продолжения MODE-02 как требующие обновления общего снимка. Затронутые проверки повторены, снимок обновляет интегратор.
- Размер `lfj8_range_control_sample_buttons` в M32R с `-Os -mmodel=medium -msdata=none` вырос с 252 до 308 байт. Новых объектов RAM нет. В обеих версиях дизассемблирование этой функции без обращений к стеку. Итоговый стек и задержка IRQ требуют общей проверки.
- Оценка расширенного состава из `check_h03_toyota_source.py` сохраняет `FAIL_BINDINGS` по `rbm_h03_application_binding` и `rbm_h03_sensor_config`. В старом сценарии без отдельного нижнего окна RX известный состав `padding-candidate` занимает 102 408 из 102 356 байт. Команда общей компоновки с нижним RX и имеющимся отчётом RAM останавливается на ещё отсутствующих привязках приложения, датчиков, ATF, селектора и часов. Размер именно итогового состава остаётся открытым.
