## Выполненная интеграция

`bench_application_profile.h` подключается из окончательного application header
вместе с пятью явными настройками владельца:

- `RBM_H03_BENCH_TOYOTA_PERIOD_TICKS`;
- `RBM_H03_BENCH_TOYOTA_MAX_LATENESS_TICKS`;
- `RBM_H03_BENCH_TOYOTA_WATCHDOG_TICKS`;
- `RBM_H03_BENCH_STARTUP_RANGE`;
- `RBM_H03_BENCH_STARTUP_REQUEST_1120`.

Частота Toyota не принимается равной H03. В источниках установлено отношение
FAST:SECONDARY:MAIN=4:2:1, но не абсолютный период. Поэтому у этих пяти настроек
нет тестового значения по умолчанию. Период, допустимое опоздание и watchdog
проверяются на единый serial-clock диапазон и обнаружение пропущенного release.

Фазовые пределы H03 выведены из существующего `bench_sensor_profile.h`:
TOP10 nominal 500 тиков, публикация через 10 TOP10, интервал 4500..5500,
возраст фазы не более 5000, команды не более 10000 тиков. Это инженерное окно
в OEM_NOMINAL шкале, а не измеренная частота. Полный пропуск публикации в него
не помещается. Живая непрерывность и соответствие регистров остаются у
существующего sensor provider.

`lfj8_h03_bench_application_profile.c` содержит действительные entry points:

| Entry point | Включение и поведение |
| --- | --- |
| `rbm_h03_bench_profile_reset_inputs` | `target_platform` → `RESET_TOYOTA_INPUTS` → проверка native MMIO, единственного ADC, владения → штатный `lfj8_h03_input_startup`. |
| `rbm_h03_bench_profile_sample_inputs` | Каждый допущенный foreground → `lfj8_h03_input_capture` с native P1/selector owner. При неподтверждённом вводе или несовпадении ожидаемой ручной передачи возвращает 0, позволяя штатному пути отозвать команду. |
| `rbm_h03_bench_profile_capture` | Release Toyota → проверка неизменяемых native IO/ADC связей → `lfj8_h03_input_capture_toyota`. Снимок и владение RAM проверяет существующий адаптер под тем же IRQ exclusion; до него retained state не читается. |

Новый второй экземпляр selector/CAN/clock/workspace не создаётся. Этот слой не
восстанавливает восемь GP из трёх raw Bosch слов и не допускает неполную нагрузку.

Обязательные **настоящие** поставщики обозначены следующими символами:

| Символ | Что должен содержать владелец |
| --- | --- |
| `rbm_h03_bench_native_input_capture` | Immutable `Lfj8H03ToyotaInputCapture` с единственным owned proposal, native binding, действительными `read_local`/`project_load` и их свежестью. |
| `rbm_h03_bench_native_input_startup` | Immutable `Lfj8H03InputStartup` из MODE-02, с согласованными окнами/временем/политикой. |
| `rbm_h03_bench_native_can_service` | Immutable `Lfj8H03TargetServiceConfig` из CAN-03, использующий существующий CAN owner, RX, TX13 и T6. |
| `rbm_h03_bench_prepare_startup_inputs` | TOY-05/владелец входов: полные начальные GP/gear, сырой приёмник и единый DTC owner; возвращает действительный `RbmU340eStartupKind`, а не константу для допуска. |

Такой контракт намеренно не заменён четырьмя фиктивными определениями. Полный
native link должен потребовать реальные объекты и функцию. Адаптации без
доказанного NVM backend используют штатный read-only fallback; профиль не
добавляет положительный ACK записи/очистки.

Подключены реальные engine context и output fragments. Для первого стенда
используется `lfj8_h03_bench_outputs.c` с `isolated_pwm_mask=0`; header отвергает
макросы, утверждающие физическую изоляцию. Обе предусмотренные output-phase
перенаправления и alias `rbm_h03_bench_phase_clock` → `control/phase_clock`
остаются обязательными для общей компоновки.

## Состав для общего компоновщика

Передать окончательный header через `--application-profile`. Компоновщик уже
включает `lfj8_h03_application_binding.c` и `lfj8_h03_target_platform.c`.
Дополнительные реальные источники этой композиции:

```text
targets/lfj8/lfj8_h03_bench_application_profile.c
targets/lfj8/bench_sensor_profile.c
targets/lfj8/lfj8_h03_engine_context.c
targets/lfj8/lfj8_h03_bench_outputs.c
```

Каждый передаётся отдельным `--binding-source`. Это включает уже существующие
`rbm_h03_application_binding`, `rbm_h03_sensor_config`, `target_clock_ready` и
`target_engine`; повторно писать их не требуется. Файл
`lfj8_h03_sensor_providers.c`, упомянутый в прежнем VSS review, в опубликованном
tree `20f42a3` отсутствует. Определения sensor config находятся именно в
`bench_sensor_profile.c`.

## Проверки и границы

Команда проверки glue без имитации целевого BIN:

```powershell
python -B targets/lfj8/check_h03_bench_application_profile.py --cc C:/msys64/mingw64/bin/gcc.exe --target host --self-test --out local/profile-host-check
```

Проверка компилирует шесть настоящих native C модулей, затем отдельный host
harness проверяет отказ при отсутствии владения, неподходящем native IO/ADC,
передачу startup/sample/capture штатным API и отсутствие лишнего чтения.
Три отрицательных компиляции проверяют отсутствие обязательных параметров,
опоздание, скрывающее второй release, и запрещённое утверждение об изоляции.
Harness и его численные значения явно `SELFTEST_ONLY` и не входят в release.

Для M32R та же утилита принимает настоящий `--profile`, `--target m32r` и
`--memory-model`. Она собирает relocatable объекты с полным журналом команд и
SHA, но не выпускает ELF/BIN и не объявляет профиль готовым к стенду. Передача
fixture/simulator header как native профиля отвергается. `--base` дополнительно
проверяет точные размер/SHA H03 по реестру.

Фактический результат текущего host прогона: `PASS_HOST_GLUE_ONLY`; все шесть
объектов и harness с тремя отрицательными компиляциями прошли. Компилятор:
native MinGW GCC 16.2.0, путь выше. `git diff --check` прошёл. Детальный журнал
и hashes: `local/profile-host-check/summary.json`.

M32R сборка, окончательное размещение и inclusive stack analysis этой порцией
не подтверждены; новые размеры Flash/RAM/стека не выдаются за измеренные.
Получение H03 и восстановление M32R toolchain выполняются другими
исполнителями. Точные ROM anchors/частоты и окончательный startup остаются
следующим связывающим шагом после их получения.

`hardware_verified:false`, `h03_identity_verified:false`, `bench_pair_ready:false`,
`flashable_image:null`. Блоки не прошивались; готовой пары этой порцией нет.
