# DTC-02 — перезапись RX15 при чтении пары BasicCAN

Порция основана на `main` `f64eff7c24744cef0fe608415039c6d10c677ff1` и включает предыдущие сданные DTC-02, в том числе `1bc3c22b18114cf8f2d5d547026fe7ac44ad9926`. Проверен исходный H03 `LFJ8-T-D.bin` с SHA-256 `844a11b809cda1f2ccaf90cb6a75666009487ccedd2e8190b7eb46137b855544`.

Парный путь `rbm_h03_dtc_rx_begin → lfj8_h03_dtc_rx_dispatch_begin → lfj8_h03_dtc_rx_queue_capture_pending` сначала читает RX15, затем RX14. Маска IRQ закрывает программное вмешательство. CAN может перезаписать RX15 до окончания чтения RX14. Если `TRFIN` уже установлен, контроллер отмечает перезапись флагом `ML`. [Renesas 32176, § 13.6.2](https://www.renesas.com/en/document/mah/32176-group-hardware-manual#page=552)

Перед выбором порядка и публикацией очереди повторно читается управляющий байт RX15, если парный обход включал RX14. При потере признака завершённого чистого приёма первый снимок отбрасывается. Исправная копия RX14 остаётся в очереди, а отметка парной доставки охватывает только опубликованный слот. Подтверждение аппаратных слотов и повтор обработки остаются у штатного обработчика. Это проверка изменения, которое видно к моменту повторного чтения управляющего байта.

## Проверки

- На предыдущей реализации M32R-тест в первом случае вернул признак обеих доставок. После правки на ПК и M32R проверены все 16 байтов чтения RX14 как моменты перезаписи RX15. Старый кадр RX15 не получает талон очереди, RX14 доставляется один раз, а при штатном повторе доставляется новый кадр RX15 с новой отметкой CAN.
- Прошли пять групп DTC foreground на ПК и M32R, 18 сравнений с исходным BasicCAN, три обхода резидентных переходов, девять сценариев сервисного допуска и путь `0x732 → 0x722`. Прошли пять тестов размещения DTC и 13 тестов компоновки.
- `build_pc_checks.py` с Zig 0.16.0 прошёл 41 шаг. В наборе Python 182 теста, один из которых требует заданного образа S03. Этот тест прошёл отдельно с закреплённым исходником.
- В отдельном проверочном worktree повторены foreground и резидентный BasicCAN с DTC-01 `58da73ce98e0933795fb9095b70955ce0f77d839` и DTC-04 `456abca6b0dda9bf8f542f1fbe90653246959443`. Нативный CAN сохраняет запрет ответа на очистку без носителя.
- В общем расчёте нижний граф вырос с 3 488 до 3 516 байт при прежних четырёх байтах статического указателя IRQ. Нижнее окно `0x006000–0x007FFF` соблюдено. Расчёт до и после правки одинаково возвращает `FAIL_BINDINGS` по семи целевым определениям, в том числе `rbm_h03_application_binding` и `rbm_h03_sensor_config`. Резидентный ELF симулятора в свои 3 592 байта включает испытательную обвязку.

```powershell
python -B tools/build_pc_checks.py --cc $zig --out local/dtc02/pc
python -B targets/lfj8/check_h03_dtc_foreground.py --cc $m32rGcc --controller $controller
python -B targets/lfj8/check_h03_dtc_basiccan.py --base $h03 --gcc $m32rGcc --with-resident-target-rx --out local/dtc02/rx.json
python -B targets/lfj8/check_h03_dtc_service_gate.py --base $h03 --gcc $m32rGcc
```

SHA-256 отчёта резидентного BasicCAN — `1be83ec250028c0f1a68fb6ee145ab641adca1295a341b5f3d6414af297c43e6`.

Аппаратная приёмка времени обработчика и перезаписи остаётся открытой. Два подтверждённых сектора DTC-04 по-прежнему отсутствуют. Блок и исходный BIN не изменялись.
