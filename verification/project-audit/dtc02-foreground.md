# DTC-02 — очередь BasicCAN в цикле CAN13

Проверка от 20.11.2026 на базе `main` `952658bff619a36f4921d637a2f0efae621f416d`. Адаптер принимает входы очередного цикла CAN13 и пару показаний монотонных микросекунд и счётчика CAN. При действительной паре он проверяет срок годности головы очереди, даже при занятом TX13. При недоступной паре диспетчер продолжает обслуживать передачу без входного кадра. [Интерфейс](../../targets/lfj8/lfj8_h03_dtc_foreground.h)

Диспетчер получает копию одного кадра. Адаптер подтверждает её по билету только после `diagnostic_consumed`. Если IRQ за это время удалил устаревшую запись и опубликовал новую, подтверждение старого билета оставляет новую запись в очереди. Владелец CAN меняет поколение и явно сбрасывает очередь после аппаратного сброса или подтверждённого освобождения слотов. Другая метка поколения сама по себе кадр не выдаёт.

Адаптер временно использует поле `received` входного блока foreground и восстанавливает его после вызова диспетчера. В объекте M32R GCC 4.8.0 с `-O2` пролог состоит из семи сохранений по 4 байта и выделения 44 байт. Собственный кадр стека составляет 72 байта. Это статическая оценка адаптера без диспетчера, его вызовов и вложенного IRQ.

## Проверка связки

На ПК и в M32R исполнены существующие захват RX14/15, очередь, диспетчер CAN13 и транспорт Chery. Состояния регистров задаёт модель.

| Сценарий | Результат |
| --- | --- |
| FIFO, занятый TX13 и Flow Control | Ответы на `10 86` и `17 FF 00` передаются по порядку на `0x722`. Кадр ждёт, пока TX13 занят. Ранний Flow Control отбрасывается. Flow Control после завершения первого кадра запускает `0x21`. При незаданной паре часов завершается предыдущий TX, голова очереди сохраняется. |
| Потеря владения и новое поколение | BusOff и возврат разрешения со старым поколением не допускают TX. После перехода `UINT32_MAX → 0` старый кадр недоступен. Явный сброс удаляет его, прежний производитель отклоняется, новый запрос передаётся. |
| Полный оборот CAN-таймера | Истёкший кадр удаляется, даже когда очередь ждёт TX13 и младшие 16 бит счётчика снова совпали. |
| IRQ между выбором и подтверждением | IRQ заменяет истёкшую запись свежей. Старое подтверждение её сохраняет, следующий цикл передаёт ответ на свежий запрос. |

Сначала собрать контроллер в соответствии с проверками PC и M32R [карты проекта](../../docs/project-map.md#команды-проверок). Для Windows использованы следующие вызовы:

```powershell
python -B targets/lfj8/check_h03_dtc_foreground.py --cc $zig --controller local/foreground/pc/controller/rbm_u340e.dll
python -B targets/lfj8/check_h03_dtc_foreground.py --cc $m32rGcc --controller local/foreground/controller/rbm_u340e_m32r_be.o
```

## Границы результата

Общий прогон ПК с Zig 0.16.0 прошёл 35 шагов. Python выполнил 69 из 70 тестов. Пропущенную сверку образа S03 повторили отдельно с указанным донором, оба теста таблицы прошли. GCC M32R 4.8.0 собрал контроллер и адаптер в объекты ELF32 big-endian. `check_h03_link.py` прошёл 17 компонентных прогонов. Повторены 15 сценариев оригинального H03 в M32R.

Для новой связки модель проверяет CAN0 через тени регистров. Точки вызова из штатного RX и реального цикла H03, размещение очереди, полную глубину стека и физическое поведение BasicCAN ещё предстоит проверить. BIN для записи не формировался.

`project_status.py --check` проходит на базовом `main`. В ветке исходники расширения очереди и foreground ожидают включения в общий снимок интегратором.
