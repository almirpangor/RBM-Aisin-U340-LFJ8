# DTC-02 — порядок кадров двух ожидающих слотов BasicCAN

Проверка от 20.11.2026 на базе `main` `b2ca79d006426a9839d64e8553cd81bf71953fe9`. Штатный обход H03 при двух заявках начинает с RX15. Метка приёма записывается вместе с данными кадра, а BasicCAN использует два чередующихся слота. Номер слота сам по себе не определяет, какой кадр принят раньше. [Трасса H03](dtc02-basiccan.md) · [Renesas 32176, §§ 13.2.1 и 13.6.2](https://www.renesas.com/en/document/mah/32176-group-hardware-manual)

`lfj8_h03_dtc_rx_queue_capture_pending` принимает снимок CAN0SLIST и одну пару часов до штатной обработки. Под одной критической секцией читает выбранные RX14/15, сверяет MSC и формат, а перед публикацией повторно проверяет доступность BasicCAN. Согласованные копии поступают в FIFO от старшей по возрасту к младшей. Возраст считается от общей 16-битной метки CAN с прежним ограничением меньше половины периода. При равных метках действует штатный порядок RX15 → RX14. Возвращаемая маска содержит только слоты, кадры которых удалось добавить. [Интерфейс](../../targets/lfj8/lfj8_h03_dtc_rx_queue.h)

Для существующих записей сохраняется порядок FIFO. Если осталось одно место, его получает более ранний допустимый кадр пары. MMIO-операции захвата состоят из чтений, подтверждение остаётся у OEM. Владелец должен назначить один путь наблюдения на попытку, чтобы пара и послотовая обёртка не опубликовали один кадр дважды.

## Прогоны

| Сценарий | Наблюдение на ПК и M32R |
| --- | --- |
| Два запроса через настоящий CAN13 | Когда `10 86` в RX14 принят раньше `17 FF 00` в RX15, переданы ответ `50`, первый кадр чтения и продолжение после Flow Control. Контрольная сборка с обращённым сравнением возраста упала на проверке первого ответа TX13. |
| Оборот 16-битного таймера и одинаковые метки | Кадр с `0xFFFE` выдан до кадра с `0x0001`. Проверены обе позиции более раннего кадра. При совпадении меток первым выдаётся RX15. |
| Проверки допуска | Потеря кадра по ML, истёкший возраст, метка позже выборки часов и прежнее поколение отсекаются. Выборка одного слота и посторонний бит CAN0SLIST не добавляют второй кадр. |
| Места в FIFO и BusOff | С одним свободным местом проходит более ранний кадр пары, прежние записи остаются. BusOff при чтении второго слота блокирует публикацию всей выборки. |

После сборки контроллера на ПК и M32R:

```powershell
python -B targets/lfj8/check_h03_dtc_foreground.py --cc $zig --controller local/basiccan-order/pc/controller/rbm_u340e.dll
python -B targets/lfj8/check_h03_dtc_foreground.py --cc $m32rGcc --controller local/basiccan-order/controller/rbm_u340e_m32r_be.o
```

Размер очереди M32R остался 172 байта. У функции парного захвата 32 байта временных копий. В объекте GCC 4.8.0 с `-Os` собственный пролог функции занимает 92 байта стека, включая сохранённые регистры. Измерение полной цепочки нового парного захвата с IRQ ещё открыто.

На ПК с Zig 0.16.0 прошли 35 шагов, включая 71 Python-тест с заданным S03. Сборка контроллера и адаптера M32R выдала объекты ELF32 big-endian, `check_h03_link.py` прошёл 17 компонентных прогонов. Отдельный верификатор очереди и CAN13 выполнил семь групп проверок на обеих архитектурах.

На той же ветке повторены 15 сравнений оригинального H03 и прежней послотовой обёртки, а также проверка старшего слова аккумулятора. Трассы маршрутов и кадры совпали с прежним прогоном. После пересборки глубина записи в стек при успешном послотовом захвате составила 216 байт. Это измерение прежней обёртки, которая не вызывает парный захват.

## Границы

Парный захват исполнен в модели регистров и связан с существующим потребителем CAN13. Открыты привязка до первой штатной очистки TRFIN, передача реальных часов и поколения CAN, выбор одного пути захвата для первоначальных заявок и последующих повторов, аппаратные тайминги и выделение RAM. Штатное обновление приложения начинается с `0x008000`. BIN для записи не формировался.

`project_status.py --check` прошёл на базовом `main`. Обновление снимка аудита и карточки для новых исходников остаётся у интегратора.
