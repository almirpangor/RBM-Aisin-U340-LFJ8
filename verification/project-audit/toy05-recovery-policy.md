# TOY-05 — восстановление адаптаций после повреждения записи

База разработки `b2ca79d006426a9839d64e8553cd81bf71953fe9`.

Донорский загрузчик UFL1 допускает возврат к предыдущей записи после
повреждения более новой. Это возвращает ранее отменённые коррекции,
если последняя запись содержала сброс. Поведение исходного загрузчика
зафиксировано в [предыдущем отчёте](toy05-adaptation-store.md).

Добавлен `rbm_u340e_runtime_restore_adaptation` для владельца запуска.
Он обновляет поля адаптаций в каноническом GP и сообщает, откуда взято
состояние. Вызывающий код передаёт подтверждённый исходный снимок и два
стабильных снимка страниц с форматом UFL1.

| Состояние слотов | Результат |
| --- | --- |
| Две валидные записи | Донорский выбор поколения, включая переход через ноль и выбор слота 0 при равенстве. Разница `80000000` считается неоднозначной |
| Валидная запись и второй читаемый слот с маркером `FFFFFFFF` | Валидная запись |
| Оба читаемых маркера `FFFFFFFF` | Исходный снимок, записи не опубликованы |
| Ошибка чтения, частичный маркер, повреждённая опубликованная запись или неоднозначный порядок | Исходный снимок, хранилище помечено недостоверным |
| Runtime не инициализирован, исходный снимок недопустим или указатели слотов пересекаются | Отказ без изменения GP |

При повреждении одного слота политика применяет исходный снимок даже при
возможности восстановить часть истории из второго слота. Функция работает
при сериализованном запуске до планирования обучения и выходов. Состояние
хранилища и разрешение выходов остаются ответственностью вызывающего кода.
Перед любым последующим сохранением владелец должен обработать состояние
недостоверного хранилища. Тестовые снимки имеют различные значения
и используются только в тесте.

## Повторённые проверки

- **Модель хранения.** Из 96 прерываний записи 93 оставляют маркер
  нетронутым и сохраняют старые коррекции, а три частичные записи маркера
  восстанавливают исходный снимок. Проверены все 768 одиночных инверсий
  в опубликованной записи для каждой из двух позиций. Во всех этих
  1536 случаях применён исходный снимок. Полностью записанный сброс
  выбирается при переходе поколения `FFFFFFFF → 00000000`. Также
  проверены пустые страницы, ошибки чтения, разница поколений
  `80000000`, отказ при некорректных входах и сохранение `GP−7184`.
- **ПК.** Zig 0.13.0. Прошли 35 из 35 шагов, включая тест контроллера
  и 71 тест Python без пропусков. Сквозной сценарий дал `PASS_OFFLINE_ONLY`.
- **Сборка M32R.** GCC 4.8.0 собрал big-endian объект контроллера
  и мост 9E1C. SHA-256 объекта контроллера
  `679b53d8f9eb00b0f74737a1fc352622e32bc495b8e251a5d75cd54f4f4477a2`.
- **Модель M32R.** Новый регрессионный сценарий прошёл в симуляторе
  контроллера. `check_h03_link.py` прошёл со штатной базой H03, входами из
  сохранённой трассы Bosch ordinary и 17 компонентными прогонами.
  Отдельно повторён [тест SLU](integration-2/slu-m32r-fixture.c) на
  65 536 значениях с проверкой force и снятия недостоверной команды.
- **Расширенная адресная модель.** В отдельном прогоне к `H03_ROOTS`
  добавлен `rbm_u340e_runtime_restore_adaptation`, к
  `CAN_EXTENSION_FILES` — `lfj8_h03_slu.c`, а к
  `CAN_EXTENSION_ROOTS` — `lfj8_h03_slu_command`. Вариант удержал
  новый символ по адресу `0x0226EC` и оставил 852 байта в основном

## Что требуется для целевого H03

Нужно получить подтверждённый исходный снимок сброса, назначить страницы
NVM и владельца операций чтения и записи, определить долговечность сброса
и записи в простое, связать обучение с остальными фазами и проверить
стек запуска. Правило для маркера `FFFFFFFF` опирается на порядок
записи маркера последним. Сценарий, в котором после успешной записи
весь маркер или вся страница снова читаются как `FF`, может скрыть уже
завершённый сброс. Для гарантии при таких отказах нужна подтверждённая
политика NVM.

Оборудование в этой порции не использовалось.
