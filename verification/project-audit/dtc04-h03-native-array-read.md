# DTC-04 — чтение внутренней Flash H03 при восстановлении DTC

База `main` — `f64eff7c24744cef0fe608415039c6d10c677ff1`. В ветку включён результат `dc2afd95a829473823c05f10eabd66142177a0dc`, который запрещает нативное подтверждение очистки без постоянного хранилища. Проверен исходный H03 `LFJ8-T-D.bin` с SHA-256 `844a11b809cda1f2ccaf90cb6a75666009487ccedd2e8190b7eb46137b855544`.

`lfj8_h03_nvm_native_restore_dtc` подключает `lfj8_h03_nvm_restore_dtc` к физическому массиву M32176F4 через `lfj8_h03_mmio`. Владелец холодного запуска передаёт два предварительно выделенных блока и единое состояние Chery DTC. Геометрия, CRC, выбор поколения и исключение ранее снятого слота остаются в существующем журнале. Читатель берёт выровненные полуслова в порядке байтов H03. Маска IRQ сохраняется на чтение обоих слотов и восстанавливается на выходе.

Перед чтением каждого слота и после него требуется `FCNT1 = 0`, `FMOD.FAENS = 1` и готовый `FSTAT` без `ERASE/WRERR`. В E/W, Virtual Flash, при недоступности, занятости или ошибке функция возвращает `LFJ8_H03_NVM_READ_FAILED`, очищая состояние холодного запуска через существующий контракт. Вызывать из штатного режима, когда код читается из Flash, владелец уже получил RAM, а DTC и сервисная запись ещё не запущены. Ветви отказа не рассчитаны на выполнение кода из Flash во время фактического программирования или стирания. [Renesas 32176, §§ 6.4.1–6.4.3](https://www.renesas.com/en/document/mah/32176-group-hardware-manual#page=139)

## Проверки

- `check_h03_nvm.py` дал одинаковый результат на ПК и M32R для модели журнала. Проверены восстановление после потери записи очистки, прерванные циклы записи и стирания, повреждение CRC и снятие старой записи.
- В отдельном ELF M32R исполнен тот же читатель и штатные функции MMIO. Тест использует RAM симулятора по адресам Flash/SFR. Прошли пустые слоты, выбор обоих слотов, переполнение поколения, повреждение нового тела и исключение старой истории при частичном снятии. Проверены отказ для шести режимов контроллера и отказ при некорректной конфигурации. Сверено восстановление маски IRQ при обоих начальных состояниях. Блоки 4 и 7 здесь служат адресами модели.
- Отдельный объект читателя занимает 372 байта кода и не добавляет статическую RAM. Измерение не включает журнал, MMIO, стек и выравнивание общей компоновки.
- В штатных путях M32R прошли исходная политика Flash, 18 сравнений BasicCAN, три обхода нижней RX-врезки и отказ отправки TX13 для `14 FF 00` при отсутствии постоянного хранилища.
- Общий прогон `check_integrated_h03.py --suite native` прошёл 22 проверки. На ПК прошёл 41 шаг, включая 179 тестов. Чистая `main` проходит `project_status.py --check`; ветка отмечает исходники двух порций для регистрации интегратором.

```powershell
python -B targets/lfj8/check_h03_nvm.py --base $h03 --gcc $m32rGcc --cc $zig --out local/dtc04/dtc-nvm.json
python -B targets/lfj8/check_h03_flash_policy.py --base $h03 --gcc $m32rGcc --out local/dtc04/flash.json
python -B targets/lfj8/check_h03_dtc_basiccan.py --base $h03 --gcc $m32rGcc --with-resident-target-rx --out local/dtc04/rx.json
```

Два прогона дали одинаковый SHA-256 `dtc-nvm.json` — `105749047cdf954973b7705485527e7660c6fb2d701aaa273f4cf0f0eb5f5c10`.

В итоговом запуске ещё нужно назначить два блока с независимым владением на всём цикле приложения и штатного обновления. Нижний сектор 4 занят резидентным RX, сектор 7 используется приложением. Для записи требуются подтверждённый способ входа в E/W по FP, драйвер из RAM, пределы ожидания и стратегия износа. Подключение восстановления к общему старту и подтверждаемой очистки к штатному сеансу зависят от этого выбора. Аппаратная приёмка, включая отключение питания, остаётся открытой. BIN для записи не формировался.
