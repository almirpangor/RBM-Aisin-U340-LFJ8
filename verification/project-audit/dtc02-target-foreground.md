# DTC-02 — привязка нативного RX к диагностическому foreground

База `main` `e24ae2ca05677df9e3a2326e43b9cbc6c67e23db`. Исходный H03 `LFJ8-T-D.bin` проверен по SHA-256 `844a11b809cda1f2ccaf90cb6a75666009487ccedd2e8190b7eb46137b855544`. Для совместного прогона взяты четыре файла владельца и адаптера CAN из опубликованной порции [CAN-03 `720bb64de67d2b64dcb9134796cf193df2951ecd`](https://github.com/almirpangor/RBM-Aisin-U340-LFJ8/commit/720bb64de67d2b64dcb9134796cf193df2951ecd).

## Интерфейс приложения

Обе RX-обёртки теперь могут вызывать `rbm_h03_dtc_rx_begin` и `rbm_h03_dtc_rx_observe` из целевого C-модуля. Одна структура приложения содержит очередь и метки парного прохода. Допуск и номер поколения приходят через `lfj8_h03_can_owner_rx_epoch`. Очередь сбрасывает CAN-03 до выдачи нового допуска. Первый послотовый проход пропускает уже опубликованный кадр, повтор использует свежую пару часов. Очистка TRFIN остаётся в штатном RX. [Интерфейс и условия вызова](../../targets/lfj8/lfj8_h03_dtc_target.h)

До первого IRQ, проходящего через новые обёртки, приложение сбрасывает привязку через `lfj8_h03_dtc_target_unbind`, инициализирует общий брокер и владельца CAN, затем устанавливает единственный объект `Lfj8H03DtcTarget`. При опросе приложения `lfj8_h03_dtc_target_poll` передаёт ту же очередь в `lfj8_h03_can_owner_poll`. Владелец один раз вызывает существующий foreground CAN13. Булев вход `native_ready` подтверждает завершение штатной инициализации и установку запрета штатных записей TX13. Диагностический тик T6 поступает от приложения отдельно.

В опубликованной порции H03-03 есть `initialize` для создания объекта и `lfj8_h03_application_running_locked` для проверки допуска перед захватом в IRQ. При окончательной стыковке нужна ранняя очистка ссылки и опрос CAN с интервалом, допустимым для общего брокера. Вызов `service_phase` там зависит от готовой фазы H03, поэтому его частоту нужно подтвердить перед использованием для CAN. [Порция H03-03 `7ced523`](https://github.com/almirpangor/RBM-Aisin-U340-LFJ8/commit/7ced52319211d394a5b1e2a8b08f9910df082018)

`CAN0TSTMP` читается между двумя отсчётами квалифицированных микросекундных часов при маскированных прерываниях. Для возраста кадра используется ранний отсчёт. Выход за заданную ширину пары передаёт владельцу признак отсутствия CAN-времени. Модель использует реальный код чтения `TML0CT` и CAN0, регистры представлены памятью симулятора. Предел 4 мкс и тик T6 в прогоне заданы испытанием. Физическая частота, непрерывность часов и период foreground требуют подтверждения.

## Проверки

- **Исходные инструкции H03.** В совместной модели foreground CAN-03 допустил пустую очередь поколения 7 после подставленного уведомления о завершении штатной настройки. Прошли 18 сравнений штатного пути с целевыми callbacks. Проверены порядок пары, ложные кадры, подмена до первого сброса TRFIN и при штатном повторе. При снятой привязке и при стёртом приложении с выставленным флагом программирования штатный RX отработал одинаково с исходным.
- **До ответа.** Из RX14 запрос `0x732 02 10 86` прошёл через очередь и foreground до выдачи в TX13 `0x722 02 50 86 00 00 00 00 00`. После выдачи ответа на первый из двух накопленных кадров модель подставила следующее уведомление setup и дренаж регистров. Foreground CAN-03 допустил поколение 8, удалил оставшийся старый кадр, вернул режим сеанса `0x9F` и оставил слот 13 в приёме без новой отправки. Проверка ответа заканчивается на записи команды TX, физической передачи в этом прогоне нет.
- **Компоненты.** На ПК и M32R прошёл отдельный набор очереди и foreground, включая многофреймовый ответ с Flow Control, переход поколения через ноль, отказ широкого замера и работу при отключённой привязке. Общие проверки ПК прошли 37 шагов, включая 102 теста. Сборки контроллера и LFJ8 для M32R и 18 компонентных прогонов `check_h03_link.py` прошли. Наборы `check_integrated_h03.py` прошли 17 сценариев native и пять components. Для GCC 4.8 исходники этих двух прогонов были скопированы во временный путь из ASCII.

```powershell
# $canOwnerDir содержит targets/lfj8 из коммита CAN-03 выше.
python -B targets/lfj8/check_h03_dtc_basiccan.py --base $h03 --gcc $m32rGcc --with-target-rx --can-owner-dir $canOwnerDir --out local/audit/dtc02-target-can03.json
```

Два прогона дали одинаковый SHA-256 JSON `72761cc22903acfa1416f3c74616d66e162b9a6c188f84f5fe078db22c4b622a`. В режиме `--with-resident-rx` отчёт предыдущей проверки нижней Flash воспроизведён побайтно. Новая сквозная сборка использует отдельную область тестового ELF в памяти симулятора. [Отчёт по нижней Flash](dtc02-h03-rx-binding.md)

## Граница передачи

В ABI M32R объект занимает 200 байт RAM, включая очередь на 172 байта и состояние прохода на 8 байт. Глобальная ссылка на объект занимает 4 байта. Таблица трёх указателей может находиться в ROM и занимает 12 байт. Максимум изменённых слов стека от входа штатного CAN0 составил 272 байта, включая целевой захват и вызовы измерения времени. Полный стек ISR и foreground требует общей компоновки.

Осталось включить вызовы жизненного цикла в результат H03-03, назначить и защитить RAM, проверить окончательное размещение кода и Virtual Flash, подтвердить установку точек ниже `0x008000` и выполнить аппаратную приёмку. Базовый `main` прошёл `project_status.py --check`. Общий снимок аудита обновляет интегратор. BIN для записи не формировался, оборудование не использовалось.
