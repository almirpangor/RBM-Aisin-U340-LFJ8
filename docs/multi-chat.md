# Работа нескольких чатов Codex

[Общий список исполнителей на GitHub](https://github.com/almirpangor/RBM-Aisin-U340-LFJ8/tree/task-board) · [Состояние ТЗ](../README.md) · [Карта подзадач](project-map.md)

## Что хранится отдельно

- В main находятся код, ТЗ, реестр готовности и доказательства.
- В task-board находятся только board.json и читаемый список исполнителей README.md.
- У каждой занятой задачи есть ID, уникальный ID чата, понятное имя, рабочая ветка, список зарезервированных файлов, дата обновления, комментарий и claim_id.
- Состояния работы — выполняется, ожидает, на проверке, завершена, освобождена. Они не заменяют статусы технической готовности из data/project-tasks.json.
- Отложенные владельцем задачи нельзя занять. Уже исследованную задачу можно занять для дальнейшего улучшения, указав конкретный новый объём в комментарии.

## Первое действие нового чата

Прочитать AGENTS.md, обновить сведения из GitHub и посмотреть общий список. Не выбирать задачу только по старой локальной копии README.

Продолжения находятся на той же странице task-board под таблицей исполнителей: **«Что осталось доделать»**. Там показаны текущая занятость и следующий шаг, ниже — сделанное, остаток и критерий приёмки каждой незакрытой задачи. Сведения берутся из data/project-tasks.json опубликованной main; отдельный список готовности вручную не ведётся. На странице указан SHA использованной main. Команда list читает актуальную main, а каждое подтверждённое изменение резерва заново публикует эту информацию в task-board.

Завершившийся чат ищет своё прежнее направление по ID чата и содержанию карточки. «Кому удобно продолжить» — рекомендация, не назначение и не резерв. Свободное продолжение занимает сам исполнитель, получая новый claim_id. Если направление уже занято, выбрать независимый остаток после проверки файлов. Номер пункта из переписки не определяет исполнителя.

Всем чатам можно отправлять один текст:

> Обнови свою копию RBM-Aisin-U340-LFJ8 из main, включая инструмент общего списка. Прочитай AGENTS.md и открой «Кто сейчас выполняет задачи» → «Что осталось доделать». Найди продолжение своего прежнего направления, проверь занятость и закрепи задачу с точными файлами. Выполни следующий шаг из карточки, проверь результат и передай опубликованный коммит в review. Если своё направление занято, возьми независимый свободный остаток без пересечения файлов.

```powershell
python -B tools/task_coordination.py list
python -B tools/project_status.py --task DTC-02
```

Выбрать доступную подзадачу и определить точные файлы изменений. Каждый чат использует **собственный owner**, например реальный ID чата либо один раз созданный UUID. Общий GitHub-логин не различает чаты. Удобное имя задаётся отдельно через label. Сохранить owner и возвращённый claim_id в контексте чата.

```powershell
python -B tools/task_coordination.py claim DTC-02 --owner <CHAT_ID> --label "Codex — диагностика" --branch codex/dtc-02-chat-a --files targets/lfj8/lfj8_h03_dtc_can.c targets/lfj8/test_lfj8_h03_dtc_can.c --note "Подключаю штатный BasicCAN RX, проверяю перезапись и поколение."
```

Заменить значения в угловых скобках своими. Правки начинать **только после успешного ответа**. Ошибка сети, занятость задачи или отказ GitHub не означают, что задача закреплена.

Если files не заданы, резервируются все пути из task.code. Можно резервировать каталог с завершающим /, например targets/lfj8/. Пути сравниваются без учёта регистра, чтобы Windows и Linux не разрешили одновременные правки одного файла.

## Рабочая копия каждого чата

Ветку, указанную при занятии, создать в отдельном worktree либо отдельной уже имеющейся копии. На одном компьютере предпочтителен worktree, который разделяет Git-объекты и не создаёт второй полный проект с донорами.

```powershell
git fetch origin main
git worktree add -b codex/dtc-02-chat-a ../RBM-U340-DTC-02 origin/main
```

**Не работать нескольким чатам в одном рабочем каталоге и не переключать чужую ветку.** tools/task_coordination.py работает из любой рабочей копии, не переключает ветку и не изменяет индекс или незавершённые правки. На другом компьютере нужно право записи в этот же репозиторий и обычная настроенная авторизация Git. Токены в файлы проекта не записываются.

На компьютере владельца пути инструментов и доноров находятся в игнорируемом local/project-paths.json. В других копиях пути настраиваются локально. Не копировать чужие абсолютные пути и не объявлять аппаратную проверку выполненной из-за отсутствия инструментария.

## Обновление, ожидание и передача

Перед записью в файлы после паузы проверить владение и обновить отметку. При длительной активной работе обновлять её примерно раз в 30 минут и после заметного результата.

```powershell
python -B tools/task_coordination.py heartbeat DTC-02 --owner <CHAT_ID> --claim-id <CLAIM_ID> --note "Декодирование проверено, добавляю сценарий перезаписи."
python -B tools/task_coordination.py block DTC-02 --owner <CHAT_ID> --claim-id <CLAIM_ID> --note "Ожидается результат CAN-03; сохранены выводы в ветке."
python -B tools/task_coordination.py resume DTC-02 --owner <CHAT_ID> --claim-id <CLAIM_ID> --note "Возобновил работу."
```

Дополнительные файлы сначала резервируются тем же heartbeat с параметром files. Список заменяется целиком, поэтому нужно перечислить и прежние сохраняемые резервы. При пересечении с другим чатом команда откажет без изменения прежнего резерва.

Задача удерживается и в ожидании, и на проверке. Время само по себе её не освобождает. Если продолжения нет, сохранить работу и освободить задачу с понятной причиной, чтобы её мог взять другой чат.

```powershell
python -B tools/task_coordination.py release DTC-02 --owner <CHAT_ID> --claim-id <CLAIM_ID> --note "Передаю работу; ветка codex/dtc-02-chat-a, осталось подключить очередь."
```

Новый чат получает новый claim_id. Старый claim_id после освобождения/повторного занятия недействителен. Если исходный чат недоступен, владелец или назначенный им интегратор явно освобождает запись по её owner и claim_id после проверки сохранённой работы. Это ручная передача, автоматического захвата давних записей нет.

## Результат и интеграция

Публиковать изменения в своей ветке, сохранять фактические результаты тестов, давать ссылку на точный коммит. Общие реестр задач, главную страницу и снимок аудита изменяет один назначенный интегратор либо чат, который отдельно зарезервировал эти файлы.

```powershell
git push -u origin codex/dtc-02-chat-a
python -B tools/task_coordination.py review DTC-02 --owner <CHAT_ID> --claim-id <CLAIM_ID> --result <FULL_COMMIT_SHA> --note "Изменение опубликовано, тесты и ограничения описаны."
```

review проверяет, что указанный полный SHA доступен в заявленной рабочей ветке на GitHub. Отметка сохраняет резерв до принятия результата. Перед завершением интегратор сверяет критерий карточки, выполняет необходимые связанные проверки, объединяет изменения и публикует main обычным push. Прямой force push для объединения не используется.

```powershell
python -B tools/task_coordination.py complete DTC-02 --owner <CHAT_ID> --claim-id <CLAIM_ID> --result <COMMIT_IN_MAIN> --note "Результат принят в main; программные проверки перечислены в отчёте."
```

complete принимает только точный SHA текущего состояния review, проверяет его присутствие в опубликованной main и освобождает резервы. Возобновление работы, переход в ожидание или изменение списка файлов через heartbeat отменяют прежнюю отметку review. После новой работы требуется снова опубликовать результат и вызвать review. Обычный heartbeat без изменения списка файлов сохраняет review. Это завершение данной порции работы, а не автоматическое признание всей функции или BIN готовыми. Статус ТЗ обновляется отдельно по доказательствам.

## Почему два чата не займут одну задачу

Каждая запись — дочерний Git-коммит от прочитанной версии task-board. Обычный fast-forward push допускает только одно из конкурирующих изменений. Проигравший клиент перечитывает список и заново проверяет задачу, рабочую ветку и пересечение файлов. Разные независимые задачи сохраняются обе; одинаковая задача или пересекающийся файл дают отказ.

После ответа сервер перечитывается. Если запись прошла, но подтверждение связи потерялось, её ID операции позволяет распознать уже сохранённый результат. Ошибка сети не считается пустым списком. Чужое содержимое существующей ветки task-board не перезаписывается.

Чтение использует уникальную временную Git-ссылку без обновления общих remote-tracking refs и FETCH_HEAD. Поэтому отдельные worktree одного проекта могут читать список одновременно. Если производитель возобновил задачу до сохранения complete, повторная проверка не позволит закрыть старую порцию поверх новой работы. Эти ограничения действуют у клиентов с актуальной версией tools/task_coordination.py; после её обновления в main обновите скрипт в своей ветке перед управлением задачей.

Это договор совместной работы чатов с правами записи в репозиторий. GitHub сам не блокирует ручное редактирование исходника в обход команды. Обязательный порядок закреплён в AGENTS.md. Повторный просмотр старого README не заменяет list/heartbeat.

## Проверки механизма

```powershell
python -B -m unittest discover -s tests -p test_task_coordination.py -v
```

Тесты используют два настоящих Git-клиента и временный локальный сервер. Проверяются одновременное занятие, отсутствие потери независимых записей, пересечение файлов и каталогов, устаревшее владение, неопубликованный результат, сбои записи/подтверждения и сохранность чужого рабочего дерева.
