# Вариант размещения рабочего состояния H03

Проверен исходный H03 `LFJ8-T-D.bin`, 524 288 байт, SHA-256 `844a11b809cda1f2ccaf90cb6a75666009487ccedd2e8190b7eb46137b855544`. Внутренний ID `LFJ8-18-9E1C`. Предпочтительный диапазон для дальнейшей проверки `[0x806B40, 0x807000)`, 1216 байт с выравниванием 64 байта. Владение им на физическом 9E1D остаётся открытым. Карта M32176F4 задаёт RAM `[0x804000, 0x80A000)`, 24 КиБ. [Идентификация H03](lfj8-9e1c-base.md) · [Renesas 32176, карта памяти][renesas]

## Что занимает RAM

| Путь исходного ROM | Фактические записи |
| --- | --- |
| `0x003D94 → 0x0009E0`, до вызова по `0x000AE0` | Задаёт SPI `0x809EFC`, FP `0x808000`. Сбрасывает `[0x808104, 0x808E06)`, пишет `FF` в `0x808100` и при входе через preamble инициализирует указатель сохранения PSW в `0x809F9C` |
| `0x008118 → 0x0404C4 → 0x009184` | Обнуляет полуинтервал `[0x804810,0x8066B4)`, 7844 байта, до основного цикла. Здесь же устанавливаются счётчики фаз и байт события |
| `0x008124 → 0x0089EC → 0x008A04` | Обнуляет первые 13 байт каждой из 16 записей с шагом 14 байт, начиная с `0x8066C4`. Последний затронутый байт `0x8067A2` |
| `0x0405C8 → 0x009184` | В условной ветви обнуляет `[0x804004,0x80480E)`. Нижняя RAM также содержит рабочие таблицы штатного приложения |
| `0x0405D0 → 0x00D4F8 → 0x00F0EC` | В той же условной ветви копирует 4096 байт из ROM `0x030022` в `[0x807000,0x808000)`. Длина из ROM `0x030020` равна `0x1000`. Сервисные пути адресуют этот массив через индексы, например в `0x00D784` и `0x00DB84` |
| `0x00C354–0x00C370 → 0x00A82C` | Перед CAN-передачей записывает 32-битную метку по `0x806B24`. Последний доказанный занятый байт непосредственно перед зазором — `0x806B27` |

Скан всех 524 288 байт исходного ROM в диапазоне кандидата не дал выровненных `LD24`, абсолютных 32-битных литералов или непосредственных адресов от штатного FP. Невыровненное совпадение `0x0000FD → 0x806C00` образовано границей двух слов векторной таблицы `0000806C 00008070`. Скрипт отдельно отмечает это совпадение. Декодирование указателей не охватывает вычисляемую адресацию, DMA, переотображение памяти и доступ из обслуживающих программ.

## Сервисная запись и границы доказательства

В ROM есть рассчитанный сервисный адресатор `0x00DBBC–0x00DC10`, чья область включает все байты кандидата. Два прямых пути к функции `0x00D574` идут из `0x00D154` и `0x00D1F0`. Общий диспетчер `0x00D108` каждый раз записывает `0x8066AC` по двум байтам конфигурации в ROM `0x03001B/0x03001C`. Оба байта точного H03 равны нулю, поэтому ветви по маскам 1 и 2 в `0x00D14E` и `0x00D1EA` пропускают вызовы независимо от прежнего значения RAM. Диспетчер достижим из обычной фоновой задачи через `0x040348`. Флаг специального режима `0x804887 == 4` не является условием этой блокировки.

Существующая конфигурация закрывает эту конкретную ветвь записи до перехода к обработчику. Отдельные диагностические чтения используют рассчитанные адреса до `0x8096FF`, например `0x045342`, а проверка диапазона регистрации диагностических указателей находится в `0x04605C–0x046072`. В карте 32176 диапазон кандидата принадлежит блоку `FESBANK0`. H03 в `0x003550–0x0035B4` меняет `FEMMOD` и `FESBANK1` для соседнего блока `0x807000`. Само отсутствие прямого обращения к `FESBANK0` не ограничивает косвенный доступ к нему. [Renesas 32176, §§ 6.4.5 и 6.6][virtual-flash]

Для целевого размещения требуется доказать, что сохранены нулевые байты профиля, а выбранные запуск, останов, служебный режим, обновление ПО и восстановление CAN не дают других записей или переотображений в окно. При входе в режим, в котором владение RAM меняется, выходы сначала остаются независимо заблокированными. На повторном захвате области её состояние инициализируется заново. Статический вывод для конкретной ветви H03 и тесты её конфигурации позволяют продолжить проверку кандидата, но пока не дают основания назначить его целевой сборке.

## Стек и рабочие объекты

В H03 активен `CR2/SPI` с началом `0x809EFC`. Общий IRQ-пролог `0x003DE0–0x003E02` сохраняет 12 слов, 48 байт, на том же стеке. Чтение `IVECT` устанавливает новый порог приоритета. Диспетчер включает прерывания перед вызовом обработчика. По правилам 32176 и настройке H03 `0x009B06–0x009B9E` семь уровней `0…6` дают верхнюю границу в 336 байт только для совместно живущих общих кадров маскируемых прерываний. К ней прибавляются живые кадры конкретных обработчиков. Ветка SBI `0x000010 → 0x003F50` добавляет 40 байт на SPI и одну 4-байтную запись в отдельном стеке PSW через `0x003E50`. Указатель последнего хранится в `0x809F9C` и растёт вниз. Оба нижних предела требуют проверки. [Renesas 32176, обработка EIT и прерываний, §§ 4 и 5.2][interrupts] · [M32R Software Manual, регистры CR2 и CR3][m32r]

Сборка M32R GCC 4.8 с `-Os -ffreestanding -fno-builtin` показывает следующие размеры. Кадры определены по `push` и резервированию `sp` в машинной сборке. Для этой версии компилятора `-fstack-usage` на M32R недоступен.

| Объект или функция | Байты | Условие |
| --- | ---: | --- |
| `RbmU340eRuntime` | 928 | Постоянное состояние |
| `FactoryGearState`, `RbmU340eHydraulicOutput`, `Lfj8H03OutputPlan` | 360, 120, 56 | Размеры входных или выходных рабочих объектов. Их размещение и время жизни задаёт общий цикл |
| `Lfj8H03Takeover` | 24 | Постоянное состояние передачи команды |
| `rbm_u340e_runtime_gears_outputs`, `rbm_u340e_outputs_step` | 52, 172 | Собственные кадры без вызываемых функций и переданного рабочего объекта |
| `factory_hydraulics_control_main → main_step → factory_phase_modes_step → factory_phase_cycle` | 572 + 212 + 180 + 152 = 1116 | Сумма четырёх кадров одного пути, без дальнейших вызовов, обёрток и IRQ |
| `lfj8_h03_takeover_prepare`, `lfj8_h03_takeover_apply` | 40, 28 | Собственные кадры без вызова переданных функций |

Набор из `RbmU340eRuntime`, takeover, пары захвата, CAN RX, диапазона, ATF, наблюдателя передачи, АЦП селектора, CAN TX, состояния драйвера и планировщика занимает 1183 байта до выравнивания и добавления других объектов. Полное рабочее пространство не помещается в окно вместе с этим набором. Перенос временных объектов в стек требует пересчёта вложенности. Надёжный предел строится по итоговому ELF и фактическому месту вызова с сохранёнными кадрами Mazda, наибольшей вложенной ветвью каждого разрешённого уровня IRQ и SBI. Отдельно требуется измерение минимального SPI и указателя PSW на изолированном стенде при запуске, восстановлении CAN и нагрузке прерываний. Сравниваются вычисленный предел, измеренный минимум и границы отведённых областей. Диагностическая граница `0x8096FF` сама по себе не задаёт нижнюю границу SPI.

## Воспроизводимые проверки

```powershell
python -B targets/lfj8/check_h03_ram_init.py --base $base --gcc $m32r
python -B targets/lfj8/check_h03_ram_candidate.py --base $base --gcc $m32r
```

Вторая проверка сначала сверяет SHA-256, затем исполняет пять изолированных неизменённых фрагментов OEM на симуляторе M32R. Каждый прогон сравнивает все 24 576 байт. Проверены очистка RAM приложения, CAN-записи, условная очистка конфигурации, проверка профиля сервисного диспетчера и заполнение служебного массива. Во всех пяти случаях кандидат сохранил исходные байты; трассы за пределами этих фрагментов требуют отдельной проверки. [Скрипт аудита](../targets/lfj8/check_h03_ram_candidate.py)
