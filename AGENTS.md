# Продолжение RBM-Aisin-U340-LFJ8

## Текущая цель и решения владельца

- Цель — отдельный TCM LFJ8-18-9E1C на H03 LFJ8-T-D.bin, Aisin U340E, Bosch ME7.9.71 E4M3.
- 20.11.2026 владелец разрешил публикацию проекта в GitHub и общий учёт задач нескольких чатов. Не прошивать блок. Не открывать PCMflash для подготовки файлов.
- Блок и резервная копия у владельца есть. Не возвращаться к запросу исходника 9E1D или фотографии наклейки.
- Два дополнительных реле и импульсный выход на панель отложены. Приём S51/S83, скорость по CAN и полный рабочий обмен остаются в первом этапе.
- Не создавать дубликат проекта. Не удалять исходники или старые артефакты в ходе обычной сверки.
- Позднейшие прямые указания пользователя имеют приоритет над этим снимком решений.

## Как начать без повторного исследования всего проекта

1. Прочитать README.md и выполнить `python -B tools/project_status.py --check`.
   Точные пути Python, компиляторов, H03 и локальных доноров сохранены в игнорируемом `local/project-paths.json`. Если Python не находится по имени, взять путь из этого файла. Проверить существование путей, а не искать инструменты заново по всему диску.
2. Выбрать задачу по запросу владельца или очереди в data/project-tasks.json. Выполнить `python -B tools/project_status.py --task ID`.
3. Читать указанные в карточке интерфейсы, реализацию, разбор и тесты. Открывать исходный PDF для неясного требования или изменения объёма, а не повторять весь аудит без причины.
4. Если проверка свежести нашла изменения, сверить только затронутые файлы, их зависимости и доказательства. Старая запись PASS не переносится автоматически на изменённый код.
5. Незавершённая зависимость не запрещает исследование или изолированную реализацию независимого фрагмента. Не подменять недостающий аппаратный результат тестовой константой.

## Границы кода

- controller/ — переносимые алгоритмы и общий GP. controller/vendor/toyota неизменяем по manifest.json; адаптацию делать в собственном слое и hydraulic_port.py.
- targets/lfj8/ — карта именно H03, датчики, CAN0, IRQ, RAM/Flash и управление выходами.
- targets/bosch/ — воспроизводимые правки S04 и проверки ST10.
- diagnostics/ — прикладные коды, статусы и сеанс. Native CAN и постоянное хранилище — отдельные задачи.
- model/, tests/ и файлы test_*/check_* — испытательные модели. Не включать их значения и callbacks в выпуск.
- targets/pcm-s05/ — исторический PCM SuperH, не активный TCM.
- Сохранить существующие пути исходников и публичные интерфейсы, если задача не требует их изменения. При переносе обновить сборки, манифесты происхождения и доказательства.

## Как завершать изменение

1. Запустить проверки карточки, затронутые изменением. Полный набор — для общего интерфейса, связанной интеграции или подготовки выпуска.
2. Сохранить фактические результаты и их границы. Отдельно отражать сборку, модель и оборудование.
3. Обновить карточку в data/project-tasks.json: сделано, осталось, критерий, код, настройки, зависимости, проверки.
4. Выполнить `python -B tools/project_status.py --write`, затем `--check`.
5. Если код изменился, обновлять verification/project-audit/2026-11-20.json либо создать новый снимок только после соответствующих проверок. Не переписывать хеши ради зелёного результата. Указывать повторённые и унаследованные проверки отдельно.
6. Журнал решений использовать для изменения требований, working-set.md — для подробных доказательств. README и project-map.md получают статусы из одного реестра.
7. Не выражать готовность BIN процентом пройденных тестов/числом задач. OFFLINE_ONLY, ELF или объект не объявлять рабочей прошивкой.
